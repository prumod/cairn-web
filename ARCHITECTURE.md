# Architecture

## Required feature organization

Follow the [feature-driven structure and check-maintenance workflow](docs/reference/project-structure.md#required-feature-driven-structure). Each page feature owns its domain rules under `pages/<feature>/domain/`, its use cases under `pages/<feature>/useCases/<useCase>/`, each with its server-function adapter, and its database repositories under `pages/<feature>/infra/`. Use cases depend on injected interfaces; adapters handle TanStack Start, Zod, request/session concerns, and concrete wiring. Backoffice implements this structure with the administrator rule in `domain/access.ts`, use case folders `useCases/changeAccess/` and `useCases/listUsers/`, and the Drizzle repository in `infra/users.server.ts`. The dependency rules distinguish these roles.

## Current system

Cairn is a Bun workspace. `apps/web` is a React and TanStack Start application built with Vite for the Cloudflare Workers runtime. The build emits the Worker entry and static client assets under `apps/web/dist`; the Worker uses the `nodejs_compat` compatibility flag. The root `bun run dev` command starts the Alchemy development stack, which serves the application locally on a Worker runtime. This is not a Node/Nitro or Express server.

The root workspace contains these application packages:

- `packages/infra` declares the Alchemy `Cloudflare.Website.Vite` resource, the per-stage Neon project and generated auth secret for cloud stages, and the local development stack. Its configured local state is not evidence of remote state or cloud provisioning.
- `packages/db` provides Drizzle schemas, migrations, and the Neon serverless HTTP database client. Migration files are generated in Drizzle Kit 1.0.0-rc.4's folder-based format under `packages/db/migrations/`; `bun run db:migrate` applies them to the local `DATABASE_URL`, and `Neon.Project` applies them to cloud-stage databases on every deploy (see [Deployment and verification limits](#deployment-and-verification-limits)).
- `packages/auth` configures Better Auth with the Drizzle adapter and Google social sign-in.
- `packages/config` contains workspace tooling configuration. UI code remains in the application; there is no separate `packages/ui` package.

TanStack Start owns UI and server routes in `apps/web/src/routes/`. Client pages and reusable client modules live in `apps/web/src/pages/` and `apps/web/src/shared/`. Shared server modules provide access bootstrap and its table for backoffice and `/api/me`; `apps/web/src/server/shared/` and `apps/web/src/services.ts` provide server-side support. Database access uses the Neon HTTP driver rather than a direct PostgreSQL wire connection.

Each router instance creates one TanStack Query `QueryClient` and provides it through the router's `Wrap` component. The backoffice uses `useQuery` for the users list and `useMutation` for access changes; successful mutations await query invalidation and refetch before controls become available again. The users query is discarded when the page has no observers. `AppLayout` clears the query cache after successful session checks and logout, and keys the authenticated outlet by user identity to remount it when accounts change.

Backoffice reads and writes use `pages/backoffice/useCases/changeAccess/changeAccess.functions.ts` and `useCases/listUsers/listUsers.functions.ts`, called through `useServerFn`. The change adapter registers a Zod input validator directly. The infrastructure-independent `useCases/changeAccess/changeAccess.ts` and `useCases/listUsers/listUsers.ts` apply the administrator rule from `domain/access.ts`, and own self-change prevention and missing-user behavior through injected interfaces. `useCases/context.server.ts` reads the current session and access facts on every call, enforces the configured origin for writes, and maps application failures to HTTP responses. `infra/users.server.ts` implements persistence. Middleware marks responses `Cache-Control: no-store`. The former users REST routes and separate RPC layer are removed.

Root dependency overrides pin `@hono/node-server` to 2.1.3 and `seroval` to 1.6.11. Alchemy depends on `@prisma/dev` 0.20.0, which requests `@hono/node-server` 1.19.9; the override crosses the major version because the audited 1.x versions contain advisories and [2.1.3 fixes the static-path decoding bypass](https://github.com/honojs/node-server/security/advisories/GHSA-rmxm-3fg6-px4f). Seroval 1.6.11 fixes the [typed-array constructor injection](https://github.com/lxsmnsyc/seroval/security/advisories/GHSA-f86p-h4j2-7qgj) and [RegExp source injection](https://github.com/lxsmnsyc/seroval/security/advisories/GHSA-9wx9-5pv9-3349) advisories; the TanStack dependency ranges allow it.

A verified Google identity matching `BOOTSTRAP_ADMIN_EMAIL` receives administrator access on its first protected request. Other users need administrator approval. Protected handlers recheck access against the database, so revocation applies to existing sessions. The company-profile page and API implementation have been removed; some acceptance scenarios still refer to them. Backoffice writes require a same-origin request. `packages/infra/src/deployment.ts` validates the main Alchemy stack configuration: local development is supported only at stage `dev`, with no custom domain, `workersDev` unset for the local runtime, `APP_ENV=development`, and revision `local`. Deployed stages are only `testing` and `production`; they map respectively to `cairn-testing.prumod.eu` and `cairn.prumod.eu`, both with `APP_ENV=production`, a required full 40-character lowercase hexadecimal `GIT_SHA`, `workersDev: false`, and `managed: true` (Alchemy owns the database and auth secret). This configures those stages for their custom domains only and disables stable `workers.dev` URLs and per-version preview URLs. The separate acceptance-only Alchemy stack supplies `APP_ENV=test`. Unsupported stages and development-mode/stage mismatches fail validation. `Alchemy.Stage` selects the stage, `Cloudflare.Website.Vite` receives the configured domain, and `Cloudflare.Worker.URL` supplies `APP_ORIGIN` and `BETTER_AUTH_URL`. Production requires an HTTPS application origin; this check is independent of Vite's build-time `NODE_ENV`. A trusted deployment process must supply the actual deployed commit; input validation alone does not attest to the running code. `/healthz` checks database connectivity and reports the Worker's `GIT_SHA` binding as `revision`. There is no seed step.

## Observability

`packages/infra/alchemy.run.ts` explicitly enables Worker observability, logs (including invocation logs), and traces. Logs and traces each use `headSamplingRate: 1`. This declares full head sampling, not a verified ingestion rate, retention period, or cost limit. There is no application OpenTelemetry exporter or automatic PostHog-to-Cloudflare trace link.

Alchemy supplies `DEPLOYMENT_STAGE` separately from `APP_ENV`: both hosted stages use `APP_ENV=production`, but only `DEPLOYMENT_STAGE=production` exposes browser analytics. `GET /api/analytics-config` returns only the public write-only project token and `https://eu.i.posthog.com`, or `null` when the stage is not production or the token is absent. Alchemy requires non-empty `POSTHOG_PROJECT_TOKEN` for production and supplies an empty token elsewhere; the acceptance stack uses stage `test` and an empty token. The token is supplied through ignored local configuration or the process environment, never committed. It is not a personal API key and grants no query access. The browser additionally validates the token's `phc_` format and the exact EU host before lazily loading `posthog-js`.

The browser disables autocapture, automatic pageview/pageleave, automatic exception capture, performance capture, and replay console capture. Replay configuration masks all text (`maskTextSelector: "*"`), inputs, and element attributes; blocks hidden/file inputs, images, video, and canvas; and disables request body/header recording. Captured network names are reduced to their origin. Non-snapshot event properties with URL, referrer, referring-domain, pathname, or search names are removed, including inside `$set` and `$set_once`; snapshots use the replay masking configuration instead. These are configured protections, not evidence from inspecting a live recording.

Explicit events are `company_profile_viewed`, `company_profile_save_attempted`, `company_profile_save_succeeded`, and `company_profile_save_failed`. Failure properties contain only HTTP `status` when available and a UUID-shaped `request_id` when available. Profile names, addresses, and radius values are not event properties. After `/api/me`, identification uses the opaque internal user ID without email or name traits. PostHog identity is held in memory and reset on logout or a confirmed missing session; a generation check prevents pending initialization from identifying a user after reset. Analytics failures do not interrupt application actions. Custom browser error listeners send generic errors with sanitized stacks; a same-origin `/assets/*.js` filename may include line/column metadata, without its query string or original error message.

Application handlers wrapped by `handleRequest` return `Cache-Control: no-store` and a generated `X-Request-ID`. Unexpected failures emit `request_failed` with `operation`, `requestId`, `revision`, `durationMs`, allowlisted `errorType`, and up to five recognized stack frames containing function name, basename, line, and column. Raw messages, request bodies, headers, and full stack paths are omitted by this application logger. This does not assert redaction of every platform invocation log. Expected denials returned as responses do not emit `request_failed`; invalid JSON returns 400 without an error log. `/healthz` returns 200 with revision after `SELECT 1`; a database execution failure is logged and returns 503, while runtime/configuration initialization failures return 500. Structured application errors have no stage field: select the stage's Worker first, then filter by revision and request ID. The browser API client retains `X-Request-ID` on `ApiError` to correlate failed profile saves with the server log; platform traces require a separate lookup.

The Vite configuration enables source-map generation for the `ssr` Worker build. A local build produced maps under `apps/web/dist/server` and none under `apps/web/dist/client`; a server map contains the application handler's source. Pinned Alchemy 2.0.0-beta.83 passes `.map` files to the Cloudflare Workers script upload with `application/source-map`, which Cloudflare's upload API accepts ([API example](https://github.com/cloudflare/cloudflare-python/blob/main/examples/workers/script_upload.py)). This confirms the intended upload path, not whether a deployed upload was accepted or Cloudflare displayed remapped frames. Cloudflare applies mapping after an uncaught exception; a stack string read or logged inside the Worker is not deobfuscated, so Cairn's sanitized `safeFrames` log field must not be treated as mapped. A live mapped exception remains unverified. Actual replay masking and live event/log/trace correlation also remain unverified. See [Investigate an application failure](docs/how-to/investigate-application-failure.md) for the bounded diagnostic procedure.

## Test runtime

Local acceptance tests build the production Worker and client assets, then run the compiled application in a test-only Alchemy `Cloudflare.Worker` stack. That stack uses local Alchemy state and `workerd`; it is not a cloud deployment. `scripts/with-test-postgres.mjs` starts disposable Docker Compose services for PostgreSQL 18.6 and a pinned Neon HTTP proxy. Test support creates isolated databases, applies the committed migrations through the Neon HTTP driver, and tears down the Worker, proxy, databases, and Compose project. Browser-controlled identities are provided by a test-only proxy outside the application; this does not exercise Google OAuth.

See [Testing](TESTING.md) for commands, latest verification, and limits.

## Enforced module boundaries

The dependency-cruiser configuration enforces public-entry-only imports and private nested implementation paths for modules under `apps/web/src/pages`, `apps/web/src/shared`, `apps/web/src/server/modules`, `apps/web/src/server/shared`, and `shared/src`. A module may use its own private implementation in its colocated unit tests; other modules cannot import that implementation or its tests. Production code cannot import tests.

The rules distinguish client modules, feature `useCases/*/*.functions.ts` RPC adapters, feature `.server.ts` implementations, plain `useCases/*/*.ts` application use cases, and `domain/` rules. Client code cannot import server-only implementations or runtime dependencies directly. Application use cases depend only on their own `useCases/<useCase>/` folder, `domain/`, and runtime-independent `shared/src`, and cannot import infrastructure adapters. Domain rules cannot import use cases or infrastructure. Module privacy prevents cross-feature private imports. Server implementations cannot import client UI; client shared modules cannot import features. The installed Start compiler also rejects client imports of `.server` files, so client-callable wrappers use `.functions.ts` and rely on compiler extraction of their server handlers.

Circular and unresolved imports fail except the runtime-resolved `cloudflare:workers` import. Restrictions include type-only imports; the cycle rule ignores type-only cycles for the generated route tree/router type relationship. See [Project structure](docs/reference/project-structure.md#currently-enforced-module-privacy-and-dependency-boundaries) for the full enforced boundaries and proof workflow.

`bun run lint:boundaries` scans application, package, infrastructure declaration/test, and shared source paths. `bun run test:boundaries` exercises accepted and rejected imports, including workspace package imports. These checks enforce dependency shape; they do not prove application behavior, OAuth, or deployment correctness. See [Project structure](docs/reference/project-structure.md).

## Deployment and verification limits

`packages/infra/alchemy.run.ts` defines an Alchemy Cloudflare `Website.Vite` stack and a Neon provider; `packages/infra/package.json` exposes `dev`, `deploy:testing`, `deploy:production`, `destroy:testing`, and `destroy:production`, with no implicit production deploy/destroy aliases.

Cloud stages (`testing`, `production`) are fully provisioned by Alchemy:

- Each stage declares a `Neon.Project` named `database` in `aws-eu-central-1` (Frankfurt). On every deploy, `Neon.Project` applies the SQL in `packages/db/migrations/`; on the first deploy, Alchemy takes over drizzle-kit's migration history.
- The Worker's `DATABASE_URL` is that project's pooled connection URI, passed as a Worker secret. No one copies it by hand.
- `BETTER_AUTH_SECRET` is generated by `Alchemy.makeRandom` and persisted in Alchemy state.
- A human supplies `NEON_API_KEY`, `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `BOOTSTRAP_ADMIN_EMAIL`, `GIT_SHA`, Cloudflare authorization for Alchemy, and `POSTHOG_PROJECT_TOKEN` for production.

The `dev` stage is unchanged: `DATABASE_URL` and `BETTER_AUTH_SECRET` come from the environment through varlock.

Two steps cannot be expressed as infrastructure code and stay manual: creating the Google OAuth Web client per environment in Google Cloud Console (no known API creates a standard Web client; unconfirmed), and the registrar nameserver/DNSSEC DS change at Spaceship.

Alchemy state is local (`Alchemy.localState()`, `.alchemy`). Remote state is not enabled, so only the machine holding `.alchemy` can update or destroy the stack. If that state is lost, the deployed resources and the generated auth secret cannot be recovered through Alchemy.

PR [#122](https://github.com/prumod/cairn-web/pull/122) merged on 2026-10-28 as `ee24e21ea46428d32d18e15006f5b011050f2b23`; its required `Agent checks` and advisory mutation report passed on tested head `d0f129da787b9b9580b439c17ae9b7a1e5bc25f7`. Testing serves the merge commit and returns that revision from `/healthz`. Production was still on `5ff1cf43fbaaff790a1d959631947424c73a27fb` during the 2026-10-28 check; deploying the merged revision there remains pending. See [Testing](TESTING.md#merged-and-hosted-verification-2026-10-28), the [deployment guide](docs/how-to/run-company-profile.md#configure-observability-inputs), and the [diagnostic guide](docs/how-to/investigate-application-failure.md) for evidence and limits. Testing telemetry queries and source-map upload are verified; original-source stack remapping and application-request-to-platform-trace correlation are not. Do not run deploy/destroy without separate explicit approval and isolated inputs. Code and local tests do not establish production readiness. A cloud cutover needs validation of provider state, migrations, OAuth, CI/security gates, and live behavior for the exact revision.

## Transcription documentation automation

`.github/workflows/agent-incorporate-transcription.yml` runs on manual dispatch and after a PR into `main` is merged with the `transcription` label (a new source) or `agent-incorporate-transcription` label (the loop's own PR). `scripts/transcriptions-pending.mjs` selects the oldest source transcription not linked from `docs/product/README.md`; the workflow skips when none is pending or while a loop PR is open. A manual run checks out the selected branch, while a merged-PR run checks out `main`. Claude Code follows `.agents/skills/incorporate-transcription/SKILL.md` and is instructed to edit only `docs/product/` and `apps/web/references/interactive-wireframe.tsx`. The workflow checks that the selected source is linked, enforces this file scope, and runs formatting, lint, and type checks before opening a labelled PR. It uses `CLAUDE_CODE_OAUTH_TOKEN` to authenticate Claude Code and `AGENT_PR_TOKEN` to push and open the PR; `GITHUB_TOKEN` PRs do not trigger the required `Agent checks`. Merging the loop PR starts another run for the next pending source. This describes configured workflow behavior; the first successful run remains unverified.

## Change contracts

- Follow the feature ownership and dependency direction in [Project structure](docs/reference/project-structure.md#required-feature-driven-structure) when placing application code. Keep cross-workspace contracts in `shared/src/` only when they do not depend on application packages.
- Keep Better Auth configuration in `packages/auth`, database schema/client/migrations in `packages/db`, and Cloudflare/Alchemy declarations in `packages/infra`.
- Do not add a parallel Node/Express runtime. Keep server-only dependencies behind the compiled server-function boundary or server routes.
- For test commands and evidence limits, see [Testing](TESTING.md).
