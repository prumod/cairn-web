# Architecture

## Current system

The Bun workspace contains a React/Vite frontend in `web/` and Node/Express backend in `backend/`. The frontend provides company-profile and access-management pages. The backend serves the built UI and API on one origin; `/` and `/access` serve the two pages and `/healthz` checks PostgreSQL and reports the revision. Vite development proxies `/api` to `127.0.0.1:3000`; Vite preview serves assets only and is not the integrated application.

Better Auth handles Google OAuth and PostgreSQL sessions; Drizzle with `pg` applies committed SQL migrations before the server listens. On a protected request, a verified Google account matching `BOOTSTRAP_ADMIN_EMAIL` is initialized as administrator. Other signed-in users await approval; administrators approve or revoke them. Every protected request checks current database access, so revocation affects existing sessions. One shared company profile stores name, address, and positive finite radius. API writes require same-origin `Origin`; requests validate basic input. No seeding is part of startup: the administrator is bootstrapped on first protected request. Browser Google OAuth was verified on historical testing revision `0e3dd2d`. Exact-revision functional E2E with real Google ID-token sessions passed on testing revision `eb8f66a54dbd6265440f72ffebe4a6be4c900224`; see [Testing](TESTING.md) for the run and coverage limits. This does not establish production readiness.

## Enforced module boundaries

`dependency-cruiser` enforces public-entry-only imports between modules and blocks circular and unresolved imports. Module production files at a module root are public entry points; nested folders are private. A module's own unit tests may import its private files. Other modules and application code may not import private files or tests. Frontend, backend, and root shared code are isolated; frontend shared code cannot depend on pages, and backend shared code cannot depend on domain modules. `bun run lint:boundaries` checks the graph and `bun run test:boundaries` proves representative allowed and forbidden imports. These import rules do not verify application behavior or deployments. See [Project structure](docs/reference/project-structure.md).

Both files specify the Render `node` runtime, Frankfurt region, Bun 1.3.14, Node 22.23.2 and runtime `NODE_ENV=production`. Only testing specifies a deployable Free plan; production requires a plan decision. The build temporarily uses `NODE_ENV=development bun install --frozen-lockfile && bun run build` to install build dependencies. `bun run start` serves the compiled application; `/healthz` is the health check. The testing Blueprint and live service now use `autoDeployTrigger: off` for serialized exact-SHA candidate deployment. GitHub Actions still runs `Agent checks` on pushes to `feat/63-company-profile` and PRs. The earlier **After CI Checks Pass** setting is historical: After `Agent checks` passed, Render marked revision `22806e08c3cd47cbda4723d686cd314fb1a076f9` Live and `/healthz` returned that full SHA. This proves one CI-gated deployment, not functional deployed E2E acceptance or Blueprint adoption. Each Blueprint's **Auto Sync** is separate; its state was not changed. The production template keeps `autoDeployTrigger: off`.

The candidate-gate workflow on `main` uses a manually dispatched `workflow_dispatch` with PR number and full candidate SHA. Dispatch explicitly approves that immutable head's build/runtime for testing; it is not automatic authorization for arbitrary forks. Before touching Render, the gate requires a current open same-repository PR to `main`, current main as its base, a candidate head that descends from current main (or is identical to it), a successful candidate PR run of `Agent checks` attached to its head SHA, and equality between GitHub's current merge candidate tree and the PR head tree. A single non-canceling global lock covers exact-SHA Render `commitId` deployment, health verification, authenticated E2E, cleanup and final status. The test service must be the reviewed Free service with automatic deployment off. Candidate/base/service/revision are rechecked before success; missing, failed, drifted or canceled work cannot be treated as success (cancellation can leave a pending status requiring rerun).

The workflow is merged and **both `Agent checks` and `Deployed company profile E2E` are required on `main`**, pinned to the GitHub Actions app, with strict checks and admin enforcement enabled. Authorized cutover stored the existing Render key in the protected main-only environment, confirmed old workflows/deployments quiescent, and disabled automatic deployment only for the existing Free testing service. The closed-PR negative dispatch failed before deployment as intended. Positive run `38929024165` proved exact-SHA deployment and Google-authenticated E2E with cleanup on candidate `777db0c9b3fdf845ff2fa3f12f18a287aa56f7a2`; branch protection was subsequently enabled with explicit approval and read back for verification. New candidate SHAs require new CI and deployed results. A live missing-status-only merge-blocking test has not yet been isolated. No Blueprint sync/adoption or production changes were performed; reconcile Blueprint ownership before any future sync.

Local, testing and production use separate PostgreSQL databases, Google OAuth clients and secrets. The testing Blueprint and production template define no Render databases or preview environments. `DATABASE_URL`, `BETTER_AUTH_SECRET`, `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET` and `BOOTSTRAP_ADMIN_EMAIL` are supplied privately with `sync: false`, never committed values. Testing fixes `APP_ORIGIN` to its existing origin; production leaves it `sync: false` until an HTTPS URL is approved. The future database target is external PostgreSQL on Neon, with production plan and cost controls still to be selected; it is not a Blueprint-managed Render database.

Testing revision `eb8f66a54dbd6265440f72ffebe4a6be4c900224` passed functional E2E for approved profile persistence and same-session approval/revocation, with matching health revision. Blueprint adoption, production provisioning, production OAuth and production data isolation remain unverified. The replacement gate and required protections have the evidence described above. Private data is protected by backend authentication and authorization; the frontend is not an access-control boundary.

Free instances have cold starts and shared workspace usage limits; `plan: free` is not a zero-spend guarantee. Render advises against Free instances for production. Review usage and overage safeguards before authorized live operations; no billing changes are implied. - Distinguish repository policy checks, historical testing observations and fresh provider/live validation. None establishes production readiness.
