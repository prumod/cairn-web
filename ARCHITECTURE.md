# Architecture

## Current system

The application is a single Bun workspace in `web/`, built with React and TanStack Start in SPA mode. File-based UI and API routes live in `web/src/routes/`; server handlers call application use cases in `web/src/server/application.server.ts`. Access and company-profile capabilities live in `web/src/server/modules/`, with auth and database support in `web/src/server/shared/`. Nitro builds the Node server in `web/.output/`. The root `bun run dev` command starts the Vite/TanStack Start development server; `bun run start` runs the built server with `web/` as its working directory. Express and a separate backend workspace have been removed.

Keep TanStack Start as the sole route owner. Do not restore the legacy `web/index.html` or `web/src/main.tsx`: Nitro auto-detects `index.html` as a renderer template, which can conflict with Start's generated route handling. Start server endpoints are file routes with `server.handlers`; the build retains these handlers even though the client uses SPA mode.

Better Auth handles Google OAuth and PostgreSQL sessions; Drizzle with `pg` applies committed SQL migrations in `web/migrations/`. Runtime configuration, database setup, migrations, and auth initialization are lazy and occur on the first server handler request. `/healthz` triggers initialization and reports database readiness and the configured revision. The root start and migration commands set the working directory to `web/`; runtime migration resolution depends on this directory. Builds do not require database or OAuth credentials.

On a protected request, a verified Google account matching `BOOTSTRAP_ADMIN_EMAIL` is initialized as administrator. Other signed-in users await approval; administrators approve or revoke them. Every protected request checks current database access, so revocation affects existing sessions. One shared company profile stores name, address, and positive finite radius. API writes require same-origin `Origin`; requests validate basic input. There is no database seed step. The current local Start tests use controlled identities and do not validate Google's OAuth flow. Earlier browser OAuth and exact-revision E2E evidence applies to the Express implementation only and does not certify the Start replacement or production readiness; see [Testing](TESTING.md).

## Enforced module boundaries

`dependency-cruiser` enforces public-entry-only imports for the UI and server modules and blocks circular and unresolved imports. Module production files at a module root are public entry points; nested folders are private. A module's own unit tests may import its private files. Other modules and application code may not import private files or tests. Client page/shared code and server modules are separated; server-shared code cannot depend on domain modules. Start route files bind framework server handlers to server-side application code. `bun run lint:boundaries` checks the graph and `bun run test:boundaries` proves representative allowed and forbidden imports. These import rules do not verify application behavior or deployments. See [Project structure](docs/reference/project-structure.md).

The build temporarily uses `NODE_ENV=development bun install --frozen-lockfile && bun run build` to install build dependencies. `bun run start` serves the compiled application; `/healthz` is the health check. The testing Blueprint and live service use `autoDeployTrigger: off` to prevent automatic deployment from interfering with exact-SHA candidate deployment. GitHub Actions runs `Agent checks` on pushes to `feat/63-company-profile` and pull requests. The earlier **After CI Checks Pass** setting and its historical deployment are not evidence for the new automatic candidate gate. Each Blueprint's **Auto Sync** is separate; its state was not changed. The production template keeps `autoDeployTrigger: off`.

`.github/workflows/trusted-pr-submission.yml` is a separate base-branch `pull_request_target` workflow limited to `opened` and `synchronize` on `main`. It filters to stable GitHub actor ID `99197066` (TiagoJacinto) and same-repository PRs. It checks out only `github.sha`, which is the base-branch workflow revision, and publishes `Trusted PR submission` for the exact current PR head. It never checks out or runs candidate code and receives no Render or testing secrets. Closed PRs, forks and other actors are not attested. Drafts do not produce attestations: a new push after marking a draft ready is required.

The automatic candidate gate in `.github/workflows/deployed-e2e.yml` listens for completed `Agent checks` workflow runs and proceeds only after a successful run for a same-repository PR to `main`. It uses trusted workflow code on `main`, not candidate code. Before contacting Render, it verifies the current open, non-draft PR and exact head SHA, current main base, candidate ancestry and GitHub merge-candidate tree, plus that the triggering run is the successful `Agent checks` run for the same PR and SHA. It also requires the `Trusted PR submission` commit status for that exact head and verifies that status points to a successful run of the attestation workflow for the same PR, SHA and account. The status is polled for up to 10 minutes to accommodate runner queue races. A single non-canceling global lock covers exact-SHA Render `commitId` deployment, health verification, authenticated E2E, cleanup and final status. The test service must be the reviewed Free service with automatic deployment off. Candidate/base/service/revision are rechecked before success; missing, failed, drifted or canceled work cannot be treated as success (cancellation can leave a pending status requiring rerun). The Render key is only used for Render operations after candidate validation; the attestation workflow does not receive it. Production is unchanged.

`Agent checks` and `Deployed company profile E2E` are required on `main`, pinned to the GitHub Actions app, with strict checks and admin enforcement enabled. Earlier manual-gate runs and the testing cutover are historical evidence for the previous workflow only; they do not demonstrate execution or deployment by the automatic workflow described here. PR #81 merged the automatic workflow into `main` as `349514a10bc65eaa50ab3d7c5761210c428d7dae`; its first actual automatic deployment remains unverified. For any candidate, each new SHA requires its own CI and deployed E2E result; earlier status does not validate subsequent changes. No Blueprint sync/adoption or production changes are part of this workflow; reconcile Blueprint ownership before any future sync.

`.github/workflows/agent-incorporate-transcription.yml` runs on `main` pushes that touch `docs/product/transcriptions/**` or `docs/product/now/funcionalidades.md`, and on manual dispatch. `scripts/transcriptions-pending.mjs` selects the next transcription not linked from `now/funcionalidades.md`; the workflow no-ops when none is pending or a PR labelled `agent-incorporate-transcription` is open. Claude Code (`ANTHROPIC_API_KEY`) edits only `docs/product/`; the workflow validates scope and formatting before opening the PR. It pushes and opens that PR with `AGENT_PR_TOKEN`, a fine-grained token of the trusted contributor, because `GITHUB_TOKEN` PRs do not trigger `Agent checks` and the candidate gate only accepts that contributor's heads. The PR passes the same required checks as any other; merging it re-runs the sensor for the next pending file. Its first run remains unverified.

Local, testing and production use separate PostgreSQL databases, Google OAuth clients and secrets. The testing Blueprint and production template define no Render databases or preview environments. `DATABASE_URL`, `BETTER_AUTH_SECRET`, `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET` and `BOOTSTRAP_ADMIN_EMAIL` are supplied privately with `sync: false`, never committed values. Testing fixes `APP_ORIGIN` to its existing origin; production leaves it `sync: false` until an HTTPS URL is approved. The future database target is external PostgreSQL on Neon, with production plan and cost controls still to be selected; it is not a Blueprint-managed Render database.

The previously recorded testing E2E on `eb8f66a54dbd6265440f72ffebe4a6be4c900224` exercised the Express implementation and is historical evidence only; the Start replacement requires fresh exact-SHA deployed E2E. Blueprint adoption, production provisioning, production OAuth and production data isolation remain unverified. The replacement gate and required protections have the evidence described above. Private data is protected by server-side authentication and authorization; client code is not an access-control boundary.

Free instances have cold starts and shared workspace usage limits; `plan: free` is not a zero-spend guarantee. Render advises against Free instances for production. Review usage and overage safeguards before authorized live operations; no billing changes are implied. ## Change contracts

- Keep client pages and shared UI code in `web/src/pages/` and `web/src/shared/`, route definitions in `web/src/routes/`, and server capabilities in `web/src/server/`. Do not add a parallel Express backend. Create root `shared/` only for genuinely reused, runtime-independent contracts.
- Distinguish repository policy checks, historical testing observations and fresh provider/live validation. None establishes production readiness.
- For test scope and test contracts, see [Testing](TESTING.md).
