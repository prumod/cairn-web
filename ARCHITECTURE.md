# Architecture

## Current system

The Bun workspace contains a React/Vite frontend in `web/` and Node/Express backend in `backend/`. The frontend provides company-profile and access-management pages. The backend serves the built UI and API on one origin; `/` and `/access` serve the two pages and `/healthz` checks PostgreSQL and reports the revision. Vite development proxies `/api` to `127.0.0.1:3000`; Vite preview serves assets only and is not the integrated application.

Better Auth handles Google OAuth and PostgreSQL sessions; Drizzle with `pg` applies committed SQL migrations before the server listens. On a protected request, a verified Google account matching `BOOTSTRAP_ADMIN_EMAIL` is initialized as administrator. Other signed-in users await approval; administrators approve or revoke them. Every protected request checks current database access, so revocation affects existing sessions. One shared company profile stores name, address, and positive finite radius. API writes require same-origin `Origin`; requests validate basic input. No seeding is part of startup: the administrator is bootstrapped on first protected request. Browser Google OAuth was verified on historical testing revision `0e3dd2d`. Exact-revision functional E2E with real Google ID-token sessions passed on testing revision `eb8f66a54dbd6265440f72ffebe4a6be4c900224`; see [Testing](TESTING.md) for the run and coverage limits. This does not establish production readiness.

## Enforced module boundaries

`dependency-cruiser` enforces public-entry-only imports between modules and blocks circular and unresolved imports. Module production files at a module root are public entry points; nested folders are private. A module's own unit tests may import its private files. Other modules and application code may not import private files or tests. Frontend, backend, and root shared code are isolated; frontend shared code cannot depend on pages, and backend shared code cannot depend on domain modules. `bun run lint:boundaries` checks the graph and `bun run test:boundaries` proves representative allowed and forbidden imports. These import rules do not verify application behavior or deployments. See [Project structure](docs/reference/project-structure.md).

## Deployment configuration and evidence

`render.yaml` targets the existing service name `cairn-testing` on `feat/63-company-profile`, at `https://cairn-testing.onrender.com` (current service ID `srv-db5aeujbc2fs73esi140`); provider adoption is not verified. `deploy/render.production.template.yaml` separately describes the future `cairn-production` service on `main`. Its `plan: __APPROVED_PRODUCTION_PLAN_REQUIRED__` records the unapproved plan decision. The file has not been validated with Render and must not be submitted until a non-Free plan is approved. No paid tier is approved. Production is unapproved and unprovisioned; checking in its template does not authorize provisioning or deployment. Blueprint adoption has not been verified.

Both files specify the Render `node` runtime, Frankfurt region, Bun 1.3.14, Node 22.23.2 and runtime `NODE_ENV=production`. Only testing specifies a deployable Free plan; production requires a plan decision. The build temporarily uses `NODE_ENV=development bun install --frozen-lockfile && bun run build` to install build dependencies. `bun run start` serves the compiled application; `/healthz` is the health check. The testing Blueprint and live service use `autoDeployTrigger: off` to prevent automatic deployment from interfering with exact-SHA candidate deployment. GitHub Actions runs `Agent checks` on pushes to `feat/63-company-profile` and pull requests. The earlier **After CI Checks Pass** setting and its historical deployment are not evidence for the new automatic candidate gate. Each Blueprint's **Auto Sync** is separate; its state was not changed. The production template keeps `autoDeployTrigger: off`.

`.github/workflows/trusted-pr-submission.yml` is a separate base-branch `pull_request_target` workflow limited to `opened` and `synchronize` on `main`. It filters to stable GitHub actor ID `99197066` (TiagoJacinto) and same-repository PRs. It checks out only `github.sha`, which is the base-branch workflow revision, and publishes `Trusted PR submission` for the exact current PR head. It never checks out or runs candidate code and receives no Render or testing secrets. Closed PRs, forks and other actors are not attested. Drafts do not produce attestations: a new push after marking a draft ready is required.

The automatic candidate gate in `.github/workflows/deployed-e2e.yml` listens for completed `Agent checks` workflow runs and proceeds only after a successful run for a same-repository PR to `main`. It uses trusted workflow code on `main`, not candidate code. Before contacting Render, it verifies the current open, non-draft PR and exact head SHA, current main base, candidate ancestry and GitHub merge-candidate tree, plus that the triggering run is the successful `Agent checks` run for the same PR and SHA. It also requires the `Trusted PR submission` commit status for that exact head and verifies that status points to a successful run of the attestation workflow for the same PR, SHA and account. The status is polled for up to 10 minutes to accommodate runner queue races. A single non-canceling global lock covers exact-SHA Render `commitId` deployment, health verification, authenticated E2E, cleanup and final status. The test service must be the reviewed Free service with automatic deployment off. Candidate/base/service/revision are rechecked before success; missing, failed, drifted or canceled work cannot be treated as success (cancellation can leave a pending status requiring rerun). The Render key is only used for Render operations after candidate validation; the attestation workflow does not receive it. Production is unchanged.

`Agent checks` and `Deployed company profile E2E` are required on `main`, pinned to the GitHub Actions app, with strict checks and admin enforcement enabled. Earlier manual-gate runs and the testing cutover are historical evidence for the previous workflow only; they do not demonstrate execution or deployment by the automatic workflow described here. The automatic workflow uses `pull_request_target`, whose workflow definition comes from the base branch, so this path becomes effective only after it is merged to `main`. The bootstrap PR may still need the currently existing manual check to satisfy branch protection. For any candidate, each new SHA requires its own CI and deployed E2E result; earlier status does not validate subsequent changes. No Blueprint sync/adoption or production changes are part of this workflow; reconcile Blueprint ownership before any future sync.

Local, testing and production use separate PostgreSQL databases, Google OAuth clients and secrets. The testing Blueprint and production template define no Render databases or preview environments. `DATABASE_URL`, `BETTER_AUTH_SECRET`, `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET` and `BOOTSTRAP_ADMIN_EMAIL` are supplied privately with `sync: false`, never committed values. Testing fixes `APP_ORIGIN` to its existing origin; production leaves it `sync: false` until an HTTPS URL is approved. The future database target is external PostgreSQL on Neon, with production plan and cost controls still to be selected; it is not a Blueprint-managed Render database.

Testing revision `eb8f66a54dbd6265440f72ffebe4a6be4c900224` passed functional E2E for approved profile persistence and same-session approval/revocation, with matching health revision. Blueprint adoption, production provisioning, production OAuth and production data isolation remain unverified. The replacement gate and required protections have the evidence described above. Private data is protected by backend authentication and authorization; the frontend is not an access-control boundary.

Free instances have cold starts and shared workspace usage limits; `plan: free` is not a zero-spend guarantee. Render advises against Free instances for production. Review usage and overage safeguards before authorized live operations; no billing changes are implied. See [Manage Render Blueprints](docs/how-to/manage-render-blueprints.md) for adoption safeguards and manual validation.
