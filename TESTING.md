# Testing

## Current test boundaries

The native Vitest configuration and `scripts/run-tests.mjs` define discovery and execution:

- Fast Vitest tests are colocated under `{web,shared}/src/**/*.{spec,test}.{ts,tsx}` and under `web/tests/{acceptance,typical}/integration/**/*.{spec,test}.{ts,tsx}`.
- Unit tests belong beside their production module and may import that module's private implementation. Non-unit acceptance/typical integration and E2E tests belong outside `src`.
- Playwright-BDD executes the approved contracts from root `features/`, with browser bindings under `web/tests/acceptance/e2e/`.

The current local Start suite has one colocated configuration unit test, 20 HTTP/PostgreSQL integration tests, and three root `features/` Playwright-BDD scenarios. The integration and browser suites exercise the built Nitro Node server; browser-only controlled identities enter through an isolated test proxy, not an application route. These tests cover local application behavior, including pending-user denial, same-session revocation, profile persistence, origin safety, auth routing, and the absence of a production test-identity route. Controlled identities do not validate Google's OAuth provider.

## Running checks

Use the commands in the root `package.json` as the source of truth. `bun run test:fast` runs Vitest in isolated PostgreSQL databases; it starts a local PostgreSQL server when available, or accepts `TEST_DATABASE_URL` for a dedicated test server with `CREATEDB`. `bun run test:browser` builds the Start app and runs the root Gherkin scenarios against its Node server plus an isolated test-only identity proxy. `bun run check` runs formatting, lint, boundaries, types, audit, fast and browser tests, and builds. Full and fast agent checks also run `bun run check:blueprints` and the Blueprint policy tests. Local checks do not prove Google OAuth or deployment configuration.

After the Express-to-Start migration, `bun run check` passed locally in the isolated migration worktree: 20 Vitest tests and three Chromium scenarios, along with build, formatting, lint, boundary, Blueprint, candidate-gate, type and dependency-audit checks. This is local controlled-fixture evidence only. Candidate `3b13fc0546dcc0ec932e0b8923c3922382fff8a2` subsequently passed CI and exact-SHA deployment/health verification in [run 38982523713](https://github.com/prumod/cairn-web/actions/runs/38982523713), but the trusted-main E2E failed its combined cleanup check. A local reproduction showed that its sign-out POST without JSON content type returns HTTP 415 and leaves the session active; a JSON `{}` POST returns 200 and invalidates the session. Do not treat historical Render health or E2E results as evidence for a Start candidate. New candidate code needs fresh `Agent checks`, exact-SHA health verification, and the required deployed functional tests before merge. Gate design and prior enforcement are described in [Agent Git gates](docs/agents/checks.md).

## Deployed functional E2E

`bun run test:deployed` runs `features/deployed/verify-company-profile.feature` against `https://cairn-testing.onrender.com`. It requires `CAIRN_CANDIDATE_SHA` (the candidate commit; not `GITHUB_SHA`, which the runner sets to the checked-out default-branch commit) and the `CAIRN_E2E_*` Google inputs, and fails closed when any are missing. It exchanges offline refresh tokens for Google ID tokens, validates identity, audience, issuer and expiry, then creates application sessions through Better Auth's ID-token sign-in. It does not test the browser redirect, state or PKCE flow; manual browser OAuth evidence stays separate. This path has not yet been revalidated for the Start replacement.

`.github/workflows/deployed-e2e.yml` uses a manual `workflow_dispatch` on `main`, with a PR number and full immutable candidate SHA. It replaces the feature-branch-only `workflow_run` automation and never checks out candidate code or downloads candidate artifacts in the privileged runner. The deployed feature defines four scenarios: pending-member denial, approval granting access in the existing session, profile persistence after reload, and same-session revocation. Each records the existing profile and member approval before changing them, then restores and verifies that baseline. These scenarios use an existing consenting member account, not a newly created Google account. They have not yet run live. Cleanup sends a JSON sign-out POST and checks that the session is null; restoration and session failures are reported separately without logging identities or response bodies. Dispatch is the trust checkpoint approving that exact PR's build/runtime code for testing; it is not an automatic test for arbitrary forks. The workflow accepts only an open, non-draft PR from this repository to `main`, at its current head, whose base is current `main` and whose candidate head descends from current `main` (or is identical to it). It requires a successful candidate PR run of `Agent checks` (GitHub attaches its status to the head SHA), and verifies that GitHub's current merge candidate has the exact PR head tree and current `main`/head parents.

The candidate gate serializes deployment, health verification, authenticated E2E, cleanup and final status publication with one non-canceling global lock. It requires the exact existing Free testing service with automatic deploy turned off, deploys the immutable SHA using Render `commitId`, waits for that exact revision, runs authenticated E2E and cleanup, then rechecks PR/base/service/live revision before publishing success. Failures or drift publish failure (once preparation succeeded); validation fails closed. Cancellation may leave a pending status and requires rerunning, not bypassing the gate. Privileged testing credentials are used only in the protected `cairn-testing-e2e` environment; trusted runner code alone does not make arbitrary candidate build/runtime code safe.

**The workflow is on `main`, and both `Agent checks` and `Deployed company profile E2E` are required there.** Strict checks and admin enforcement remain enabled; both contexts are pinned to the GitHub Actions app. The authorized testing cutover stored the existing Render key privately as `CAIRN_RENDER_API_KEY` in the main-only environment and verified testing automatic deployment is off; the service remains Free. `render.yaml` and its policy require `off` to prevent interference with exact-SHA deployment. No Blueprint sync or adoption was performed. Live negative [run 38927827211](https://github.com/prumod/cairn-web/actions/runs/38927827211) rejected a closed PR before deployment, as intended. Positive [run 38929024165](https://github.com/prumod/cairn-web/actions/runs/38929024165) validated and deployed exact candidate `777db0c9b3fdf845ff2fa3f12f18a287aa56f7a2`, passed Google-authenticated E2E and cleanup, and published success after drift checks. Every subsequent candidate SHA must obtain its own result. The negative run proves candidate rejection, not an isolated live missing-status merge-blocking test.

## Blueprint checks and live evidence

`bun run check:blueprints` parses `render.yaml` and `deploy/render.production.template.yaml` with Bun's native YAML parser and checks the repository's closed deployment policy. The production template must retain `plan: __APPROVED_PRODUCTION_PLAN_REQUIRED__` until a non-Free plan is explicitly approved. The placeholder preserves the unresolved plan decision; local policy success is not provider validation. Do not submit the template until a non-Free plan is approved and provider validation is run. No paid tier is approved. `scripts/check-blueprints.test.mjs` exercises allowed and rejected policy cases; full and fast checks include these tests. This verifies local syntax and policy, not Render's complete schema, account permissions, resource adoption, branch availability or running services. Provider schema/Blueprint validation and an inspection of proposed actions remain separate gates before any authorized sync. See [Manage Render Blueprints](docs/how-to/manage-render-blueprints.md).

Historical deployed functional E2E passed against exact testing revision `eb8f66a54dbd6265440f72ffebe4a6be4c900224` in [run 38921040473](https://github.com/prumod/cairn-web/actions/runs/38921040473), including Google ID-token sessions, profile persistence, revocation, baseline restoration and sign-out. That revision used Express; the result does not certify the Start replacement. Its scenario started from an approved member. The current Start feature adds pending-before-approval and approval-in-existing-session scenarios, but they have not been run live. Its candidate status was `success`; that optional status is not merge enforcement. Browser-redirect OAuth evidence is separate. Blueprint adoption and production readiness remain unverified; replacement-gate and protection evidence is described above. No live operation is part of the local Blueprint check.

Tests describe observable behavior and system boundaries. Update relevant tests when those contracts change; test-file discovery and runnable commands remain defined by the package scripts, test configuration, and test runner.
