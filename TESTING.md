# Testing

## Current test boundaries

The native Vitest configuration and `scripts/run-tests.mjs` define discovery and execution:

- Fast Vitest tests are colocated under `{web,shared}/src/**/*.{spec,test}.{ts,tsx}` and under `web/tests/{acceptance,typical}/integration/**/*.{spec,test}.{ts,tsx}`.
- Unit tests belong beside their production module and may import that module's private implementation. Non-unit acceptance/typical integration and E2E tests belong outside `src`.
- Playwright-BDD executes the approved contracts from root `features/`, with browser bindings under `web/tests/acceptance/e2e/`.

The current local Start suite has one colocated configuration unit test, 20 HTTP/PostgreSQL integration tests, eight HTTP sign-in adapter tests, and three root `features/` Playwright-BDD scenarios. The integration and browser suites exercise the built Nitro Node server; browser-only controlled identities enter through an isolated test proxy, not an application route. These tests cover local application behavior, including pending-user denial, same-session revocation, profile persistence, origin safety, auth routing, and the absence of a production test-identity route. Controlled identities do not validate Google's OAuth provider.

## Running checks

Use the commands in the root `package.json` as the source of truth. `bun run test:fast` runs Vitest in isolated PostgreSQL databases; it starts a local PostgreSQL server when available, or accepts `TEST_DATABASE_URL` for a dedicated test server with `CREATEDB`. `bun run test:browser` builds the Start app and runs the root Gherkin scenarios against its Node server plus an isolated test-only identity proxy. `bun run check` runs formatting, lint, boundaries, types, audit, fast and browser tests, and builds. Full and fast agent checks also run `bun run check:blueprints` and the Blueprint policy tests. Local checks do not prove Google OAuth or deployment configuration.

After the Express-to-Start migration, `bun run check` passed locally in the isolated migration worktree: 20 Vitest tests and three Chromium scenarios, along with build, formatting, lint, boundary, Blueprint, candidate-gate, type and dependency-audit checks. This is local controlled-fixture evidence only. Candidate `3b13fc0546dcc0ec932e0b8923c3922382fff8a2` subsequently passed CI and exact-SHA deployment/health verification in [run 38982523713](https://github.com/prumod/cairn-web/actions/runs/38982523713), but the trusted-main E2E failed its combined cleanup check. A local reproduction showed that its sign-out POST without JSON content type returns HTTP 415 and leaves the session active; a JSON `{}` POST returns 200 and invalidates the session. The candidate bindings now send JSON, check session invalidation, and report separate restoration/sign-out failures without logging identities or response bodies. PR #76 merged the correction into trusted `main` as `40abb4d66a8fdfe460d2ee7a0109cbe9399613ca`. No successful Start deployed E2E is claimed.

The existing candidate gate and branch-protection evidence below predates the Start replacement. It describes the gate's prior operation, not successful functional E2E of the new runtime. Do not treat historical Render health or E2E results as evidence for a Start candidate. New candidate code needs fresh `Agent checks`, exact-SHA health verification, and the required deployed functional tests before merge. Gate design and prior enforcement are described in [Agent Git gates](docs/agents/checks.md).

## Deployed functional E2E

`bun run test:deployed` runs `features/deployed/verify-company-profile.feature` against `https://cairn-testing.onrender.com`. It requires `CAIRN_CANDIDATE_SHA` (the candidate commit; not `GITHUB_SHA`, which the runner sets to the checked-out default-branch commit) and the `CAIRN_E2E_*` Google inputs, and fails closed when any are missing. It exchanges offline refresh tokens for Google ID tokens, validates identity, audience, issuer and expiry, then creates application sessions through Better Auth's ID-token sign-in. It does not test the browser redirect, state or PKCE flow; manual browser OAuth evidence stays separate. This path has not yet been revalidated for the Start replacement.

The automatic `.github/workflows/deployed-e2e.yml` listens for successful `Agent checks` completion. It only proceeds for an open, non-draft, same-repository PR to `main` and validates that the CI run, PR number and exact current head SHA match. A separate `.github/workflows/trusted-pr-submission.yml` uses base-branch `pull_request_target`, only `opened`/`synchronize`, and filters to TiagoJacinto's stable GitHub actor ID. That workflow checks out only `github.sha` (the base-branch revision), posts a `Trusted PR submission` status for the exact current PR head, and neither checks out/runs candidate code nor receives Render/testing secrets. The deployed gate verifies the status points to a successful attestation workflow run for the same PR, SHA and account; it polls for up to 10 minutes to account for runner queue races. The Render key is used for Render operations only after validation succeeds. The gate then keeps the existing exact-SHA, tree, current-base, service and non-canceling lock guards, deploys via Render `commitId`, checks the exact live revision, runs authenticated E2E and cleanup, and rechecks before final status. Validation fails closed; failures or drift do not publish success, and cancellation may leave a pending status that requires rerunning.

The candidate gate serializes deployment, health verification, authenticated E2E, cleanup and final status publication with one non-canceling global lock. It requires the exact existing Free testing service with automatic deploy turned off, deploys the immutable SHA using Render `commitId`, waits for that exact revision, runs authenticated E2E and cleanup, then rechecks PR/base/service/live revision before publishing success. Failures or drift publish failure (once preparation succeeded); validation fails closed. Cancellation may leave a pending status and requires rerunning, not bypassing the gate. Privileged testing credentials are used only in the protected `cairn-testing-e2e` environment; trusted runner code alone does not make arbitrary candidate build/runtime code safe.

**The workflow is on `main`, and both `Agent checks` and `Deployed company profile E2E` are required there.** Strict checks and admin enforcement remain enabled; both contexts are pinned to the GitHub Actions app. The authorized testing cutover stored the existing Render key privately as `CAIRN_RENDER_API_KEY` in the main-only environment and verified testing automatic deployment is off; the service remains Free. `render.yaml` and its policy require `off` to prevent interference with exact-SHA deployment. No Blueprint sync or adoption was performed. Live negative [run 38927827211](https://github.com/prumod/cairn-web/actions/runs/38927827211) rejected a closed PR before deployment, as intended. Positive [run 38929024165](https://github.com/prumod/cairn-web/actions/runs/38929024165) validated and deployed exact candidate `777db0c9b3fdf845ff2fa3f12f18a287aa56f7a2`, passed Google-authenticated E2E and cleanup, and published success after drift checks. Every subsequent candidate SHA must obtain its own result. The negative run proves candidate rejection, not an isolated live missing-status merge-blocking test.

### Sign-in rate-limit handling

A local production-enabled Better Auth probe accepted three rapid social sign-in requests and rejected the fourth with HTTP 429 and `X-Retry-After: 10`. The expanded suite performs eight sign-ins, making rate limiting a plausible explanation for the live sequence, not a proven live diagnosis. The runner now reports only the failed HTTP status and honors numeric `Retry-After` or `X-Retry-After` seconds on explicit 429 responses. It permits at most three requests, rejects missing/malformed or greater-than-15-second intervals, and never retries other statuses or transport errors. Application rate limits are unchanged. Eight local HTTP adapter tests cover waiting, retry bounds, both headers, invalid intervals and non-rate-limit failures; they use no Google credentials. PR #79 merged this runner change into trusted `main` as `f0e68986ee4e0ad394c1db74b868a7f69e3644c7`. Before that merge, an explicitly authorized, SHA-pinned isolated bootstrap runner passed all four Google scenarios and cleanup against the Express candidate in [run 39020936493](https://github.com/prumod/cairn-web/actions/runs/39020936493). The temporary environment branch policy was removed after job admission, and main-only access was verified again after completion. The bootstrap branch is not for merging. This result validates the repaired runner against Express, not Start; the integrated Start candidate still needs its own successful exact-SHA run.

## Blueprint checks and live evidence

`bun run check:blueprints` parses `render.yaml` and `deploy/render.production.template.yaml` with Bun's native YAML parser and checks the repository's closed deployment policy. The production template must retain `plan: __APPROVED_PRODUCTION_PLAN_REQUIRED__` until a non-Free plan is explicitly approved. The placeholder preserves the unresolved plan decision; local policy success is not provider validation. Do not submit the template until a non-Free plan is approved and provider validation is run. No paid tier is approved. `scripts/check-blueprints.test.mjs` exercises allowed and rejected policy cases; full and fast checks include these tests. This verifies local syntax and policy, not Render's complete schema, account permissions, resource adoption, branch availability or running services. Provider schema/Blueprint validation and an inspection of proposed actions remain separate gates before any authorized sync. See [Manage Render Blueprints](docs/how-to/manage-render-blueprints.md).

Historical deployed functional E2E passed against exact testing revision `eb8f66a54dbd6265440f72ffebe4a6be4c900224` in [run 38921040473](https://github.com/prumod/cairn-web/actions/runs/38921040473), including Google ID-token sessions, profile persistence, revocation, baseline restoration and sign-out. That revision used Express; the result does not certify the Start replacement. Its scenario started from an approved member. The current feature adds pending-before-approval and approval-in-existing-session scenarios; all four scenarios passed against the Express candidate in run 39020936493, but have not all passed against Start. Its candidate status was `success`; that optional status is not merge enforcement. Browser-redirect OAuth evidence is separate. Blueprint adoption and production readiness remain unverified; replacement-gate and protection evidence is described above. No live operation is part of the local Blueprint check.

Tests describe observable behavior and system boundaries. Update relevant tests when those contracts change; test-file discovery and runnable commands remain defined by the package scripts, test configuration, and test runner.
