# Testing

## Current test boundaries

The native Vitest configuration and `scripts/run-tests.mjs` define discovery and execution:

- Fast Vitest tests are colocated under `{web,backend,shared}/src/**/*.{spec,test}.{ts,tsx}` and under `{web,backend}/tests/{acceptance,typical}/integration/**/*.{spec,test}.{ts,tsx}`.
- Unit tests belong beside their production module and may import that module's private implementation. Non-unit acceptance/typical integration and e2e tests belong outside `src`.
- Playwright-BDD executes the approved contracts from root `features/`, with browser bindings under `web/tests/acceptance/e2e/`. The legacy browser feature location is removed.

Current coverage includes one colocated configuration unit test, 18 HTTP/PostgreSQL integration tests, and three root `features/` Playwright-BDD scenarios. The scenarios and controlled identities exercise real app/database behavior but do not validate Google's actual OAuth provider. Fresh OAuth and live deployment checks remain separate from these controlled tests.

## Running checks

Use the commands in the root `package.json` as the source of truth. `bun run test:fast` runs Vitest in an isolated PostgreSQL database; it starts a local PostgreSQL server when available, or accepts `TEST_DATABASE_URL` for a dedicated test server with `CREATEDB`. `bun run test:browser` runs the root Gherkin scenarios against a fixture Express server and disposable PostgreSQL; the fixture's private test identity endpoint exists only in the test server, not production. `bun run check` runs formatting, lint, boundaries, types, audit, tests, and builds. Full and fast agent checks also run `bun run check:blueprints` and the Blueprint policy tests. These local checks do not prove OAuth-provider or deployment configuration. GitHub Actions `Agent checks` runs on pull requests and pushes to `main` and `feat/63-company-profile`. The earlier Render **After CI Checks Pass** setting and its historical deployment are not evidence that the new automatic deployed-E2E workflow has executed. Agent gates are described in [Agent Git gates](docs/agents/checks.md).

## Deployed functional E2E

`bun run test:deployed` runs `features/deployed/verify-company-profile.feature` against `https://cairn-testing.onrender.com`. It requires `CAIRN_CANDIDATE_SHA` (the candidate commit; not `GITHUB_SHA`, which the runner sets to the checked-out default-branch commit) and the `CAIRN_E2E_*` Google inputs, and fails closed when any are missing. It exchanges offline refresh tokens for Google ID tokens, validates identity, audience, issuer and expiry, then creates application sessions through Better Auth's ID-token sign-in. It does not test the browser redirect, state or PKCE flow; manual browser OAuth evidence stays separate. The four scenarios cover pending-member denial, approval granting access in the existing session, profile persistence after reload, and same-session revocation. Each records the existing profile and member approval before changing them, then restores and verifies that baseline. They use an existing consenting member account, not a newly created Google account. Cleanup sends a JSON sign-out POST and checks that the session is null; restoration and session failures are reported separately without logging identities or response bodies.

The automatic `.github/workflows/deployed-e2e.yml` listens for successful `Agent checks` completion. It only proceeds for an open, non-draft, same-repository PR to `main` and validates that the CI run, PR number and exact current head SHA match. A separate `.github/workflows/trusted-pr-submission.yml` uses base-branch `pull_request_target`, only `opened`/`synchronize`, and filters to TiagoJacinto's stable GitHub actor ID. That workflow checks out only `github.sha` (the base-branch revision), posts a `Trusted PR submission` status for the exact current PR head, and neither checks out/runs candidate code nor receives Render/testing secrets. The deployed gate verifies the status points to a successful attestation workflow run for the same PR, SHA and account; it polls for up to 10 minutes to account for runner queue races. The Render key is used for Render operations only after validation succeeds. The gate then keeps the existing exact-SHA, tree, current-base, service and non-canceling lock guards, deploys via Render `commitId`, checks the exact live revision, runs authenticated E2E and cleanup, and rechecks before final status. Validation fails closed; failures or drift do not publish success, and cancellation may leave a pending status that requires rerunning.

Forks, other actors, closed PRs and drafts are not deployed. Since attestations are created only for `opened` and `synchronize`, a draft needs a new push after becoming ready. Both `Agent checks` and `Deployed company profile E2E` are required on `main`. `pull_request_target` uses workflow code from the base branch, so the new path takes effect only after merge; the bootstrap PR may still need the currently existing manual check to satisfy branch protection. Production is unchanged. This new workflow has not been demonstrated in a live execution or deployment. Earlier manual-gate runs are historical evidence for the previous path only, not for this automatic workflow.

## Blueprint checks and live evidence

`bun run check:blueprints` parses `render.yaml` and `deploy/render.production.template.yaml` with Bun's native YAML parser and checks the repository's closed deployment policy. The production template must retain `plan: __APPROVED_PRODUCTION_PLAN_REQUIRED__` until a non-Free plan is explicitly approved. The placeholder preserves the unresolved plan decision; local policy success is not provider validation. Do not submit the template until a non-Free plan is approved and provider validation is run. No paid tier is approved. `scripts/check-blueprints.test.mjs` exercises allowed and rejected policy cases; full and fast checks include these tests. This verifies local syntax and policy, not Render's complete schema, account permissions, resource adoption, branch availability or running services. Provider schema/Blueprint validation and an inspection of proposed actions remain separate gates before any authorized sync. See [Manage Render Blueprints](docs/how-to/manage-render-blueprints.md).

A previous deployed functional scenario passed against exact testing revision `eb8f66a54dbd6265440f72ffebe4a6be4c900224` in [run 38921040473](https://github.com/prumod/cairn-web/actions/runs/38921040473), including Google ID-token sessions, persistence, pending-state read/write denial after revocation, baseline restoration and sign-out. This is historical evidence from the prior manual path, not execution of the new automatic workflow; the candidate status was optional and is not merge enforcement. Browser-redirect OAuth evidence is separate. Blueprint adoption and production readiness remain unverified. No live operation is part of the local Blueprint check.

Tests describe observable behavior and system boundaries. Update relevant tests when those contracts change; test-file discovery and runnable commands remain defined by the package scripts, test configuration, and test runner.
