# Testing

## Current test boundaries

The native Vitest configuration and `scripts/run-tests.mjs` define discovery and execution:

- Fast Vitest tests are colocated under `{web,backend,shared}/src/**/*.{spec,test}.{ts,tsx}` and under `{web,backend}/tests/{acceptance,typical}/integration/**/*.{spec,test}.{ts,tsx}`.
- Unit tests belong beside their production module and may import that module's private implementation. Non-unit acceptance/typical integration and e2e tests belong outside `src`.
- Playwright-BDD executes the approved contracts from root `features/`, with browser bindings under `web/tests/acceptance/e2e/`. The legacy browser feature location is removed.

Current coverage includes one colocated configuration unit test, 18 HTTP/PostgreSQL integration tests, and three root `features/` Playwright-BDD scenarios. The scenarios and controlled identities exercise real app/database behavior but do not validate Google's actual OAuth provider. Fresh OAuth and live deployment checks remain separate from these controlled tests.

## Running checks

Use the commands in the root `package.json` as the source of truth. `bun run test:fast` runs Vitest in an isolated PostgreSQL database; it starts a local PostgreSQL server when available, or accepts `TEST_DATABASE_URL` for a dedicated test server with `CREATEDB`. `bun run test:browser` runs the root Gherkin scenarios against a fixture Express server and disposable PostgreSQL; the fixture's private test identity endpoint exists only in the test server, not production. `bun run check` runs formatting, lint, boundaries, types, audit, tests, and builds. Full and fast agent checks also run `bun run check:blueprints` and the Blueprint policy tests. These local checks do not prove OAuth-provider or deployment configuration. GitHub Actions `Agent checks` runs on pull requests and pushes to `main` and `feat/63-company-profile`. The existing Render service's **After CI Checks Pass** setting was verified after reloading the Render page. After `Agent checks` passed, Render marked revision `22806e08c3cd47cbda4723d686cd314fb1a076f9` Live and `/healthz` returned that full SHA. This proves one CI-gated deployment, not functional deployed E2E acceptance. Render does not deploy when it detects zero checks or any failing check; GitHub conclusions `success`, `neutral` and `skipped` count as passing. Agent gates are described in [Agent Git gates](docs/agents/checks.md).

## Deployed functional E2E

`bun run test:deployed` runs `features/deployed/verify-company-profile.feature` against `https://cairn-testing.onrender.com`. It requires `CAIRN_CANDIDATE_SHA` (the candidate commit; not `GITHUB_SHA`, which the runner sets to the checked-out default-branch commit) and the `CAIRN_E2E_*` Google inputs, and fails closed when any are missing. It exchanges offline refresh tokens for Google ID tokens, validates identity, audience, issuer and expiry, then creates application sessions through Better Auth's ID-token sign-in. It does not test the browser redirect, state or PKCE flow; manual browser OAuth evidence stays separate.

`.github/workflows/deployed-e2e.yml` uses a manual `workflow_dispatch` on `main`, with a PR number and full immutable candidate SHA. It replaces the feature-branch-only `workflow_run` automation and never checks out candidate code or downloads candidate artifacts in the privileged runner. The deployed scenario covers an approved member's save, reload, and same-session revocation, not first-time sign-in awaiting approval. Dispatch is the trust checkpoint approving that exact PR's build/runtime code for testing; it is not an automatic test for arbitrary forks. The workflow accepts only an open, non-draft PR from this repository to `main`, at its current head, whose base is current `main` and whose candidate head descends from current `main` (or is identical to it). It requires a successful candidate PR run of `Agent checks` (GitHub attaches its status to the head SHA), and verifies that GitHub's current merge candidate has the exact PR head tree and current `main`/head parents.

The candidate gate serializes deployment, health verification, authenticated E2E, cleanup and final status publication with one non-canceling global lock. It requires the exact existing Free testing service with automatic deploy turned off, deploys the immutable SHA using Render `commitId`, waits for that exact revision, runs authenticated E2E and cleanup, then rechecks PR/base/service/live revision before publishing success. Failures or drift publish failure (once preparation succeeded); validation fails closed. Cancellation may leave a pending status and requires rerunning, not bypassing the gate. Privileged testing credentials are used only in the protected `cairn-testing-e2e` environment; trusted runner code alone does not make arbitrary candidate build/runtime code safe.

**The workflow is on `main`, but required-status enforcement remains unfinished.** The authorized testing cutover stored the existing Render key privately as `CAIRN_RENDER_API_KEY` in the main-only environment and verified testing automatic deployment is off; the service remains Free. `render.yaml` and its policy require `off` to prevent interference with exact-SHA deployment. No Blueprint sync or adoption was performed. Live negative [run 38927827211](https://github.com/prumod/cairn-web/actions/runs/38927827211) rejected a closed PR before deployment, as intended. Positive live proof of this replacement workflow is still required. `main` requires only `Agent checks`; an optional status does not satisfy the original enforced-gate requirement.

## Blueprint checks and live evidence

`bun run check:blueprints` parses `render.yaml` and `deploy/render.production.template.yaml` with Bun's native YAML parser and checks the repository's closed deployment policy. The production template must retain `plan: __APPROVED_PRODUCTION_PLAN_REQUIRED__` until a non-Free plan is explicitly approved. The placeholder preserves the unresolved plan decision; local policy success is not provider validation. Do not submit the template until a non-Free plan is approved and provider validation is run. No paid tier is approved. `scripts/check-blueprints.test.mjs` exercises allowed and rejected policy cases; full and fast checks include these tests. This verifies local syntax and policy, not Render's complete schema, account permissions, resource adoption, branch availability or running services. Provider schema/Blueprint validation and an inspection of proposed actions remain separate gates before any authorized sync. See [Manage Render Blueprints](docs/how-to/manage-render-blueprints.md).

The deployed functional scenario passed against exact testing revision `eb8f66a54dbd6265440f72ffebe4a6be4c900224` in [run 38921040473](https://github.com/prumod/cairn-web/actions/runs/38921040473), including Google ID-token sessions, persistence, pending-state read/write denial after revocation, baseline restoration and sign-out. Its candidate status was `success`; that optional status is not merge enforcement. Browser-redirect OAuth evidence is separate. Blueprint adoption, the replacement candidate gate, required-status enforcement and production readiness still need evidence. No live operation is part of the local Blueprint check.

Tests describe observable behavior and system boundaries. Update relevant tests when those contracts change; test-file discovery and runnable commands remain defined by the package scripts, test configuration, and test runner.
